## 3. Что работает по-настоящему

Проверено запросами к боевой базе и прогоном сценариев в браузере.

**Инфраструктура**
- Postgres (Supabase, Frankfurt) с построчной защитой доступа (RLS) на всех таблицах
- Анонимная авторизация: пользователь получает данные сразу, до ввода телефона
- Вход по коду **через Telegram-бота** вместо платных SMS (0 ₽ за код)
- Резервный канал в Россию: Yandex Cloud API Gateway + Cloud Function перед Supabase
- Обновления «по воздуху» через EAS Update — новая версия у тестировщиков без пересборки

**Данные кладбища** (это главный актив)
- DWG-съёмка геодезиста разобрана в геометрию
- Координаты пересчитаны МСК-47 зона 2 → WGS-84, проверены тремя способами
- Многостраничный план в PDF — `docs/cemetery/cemetery-plan.pdf`
- GeoJSON для внешних систем — `docs/cemetery/cemetery-wgs84.geojson`
- Пересборка данных одной командой: `python3 tools/cemetery/export_app.py`

**Функции приложения**
- Поиск человека по имени, городу, кладбищу
- Карточка памяти: биография, фотогалерея, карта, участок
- Карта кладбища: план, поиск по номеру, пеший маршрут в Яндекс.Картах
- Свеча памяти — горит 24 часа, состояние общее для всех
- Книга воспоминаний — записи от родственников
- Сохранённые могилы, приглашение родственников, QR-код
- Памятные даты с локальными напоминаниями
- Создание заказа с выбором услуги, даты и повтора
- Список и статусы заказов

## 4. Что заглушка — прямым текстом

### Оплата — не работает

`packages/api/src/endpoints.ts:321`. Все три метода `paymentsApi` возвращают
фикстуру даже на боевой базе:

```ts
create()  → { paymentId: 'pay-<timestamp>', confirmationUrl: 'https://yookassa.ru/mock' }
status()  → { status: 'succeeded', amount: 800 }
methods() → список карт из фикстур
```

Заказ действительно создаётся в базе и получает статус «оплачен», но **денег
не списывается**. Именно поэтому платных заказов ровно 0 — не потому, что их
не заказали, а потому что заплатить физически невозможно.

Чтобы включить: нужно юрлицо (ООО или ИП), договор с ЮКассой, серверная часть
для webhook подтверждения платежа. Это не про код — это про регистрацию бизнеса.

### Приложение исполнителя — не работает с базой

`packages/api/src/endpoints.ts:551–599`. Все 10 методов на фикстурах:
список заказов, принять, отклонить, начать, завершить, фото до/после,
чек-лист, профиль, онлайн-статус.

### Загрузка фотографий — некуда сохранять

Экраны фотоотчёта готовы и показывают сетки «до/после», но Supabase Storage
не подключён. `uploadBefore`/`uploadAfter` возвращают `{ success: true }`,
ничего не сохраняя. На демо-карточках фотографии — заглушки.

### Push-уведомления — только каркас

`apps/client/src/lib/notifications.ts`: права запрашиваются, токен получается,
обработчик стоит. Отправлять некому — нет ключей FCM/APNs и серверной отправки.
Памятные даты работают через **локальные** уведомления телефона — они реальные,
но живут только на устройстве.

### Подписка — экран без покупок

Три тарифа нарисованы, оплаты нет по той же причине, что и в п. «Оплата».
Все пользователи фактически на «Базовом».

### Демо-кладбища

8 из 9 кладбищ (Новодевичье, Хованское, Ваганьковское и др.) — записи
справочника без планов и без реальных захоронений. Нужны, чтобы поиск и
фильтры не выглядели пустыми. На карту ведёт только Даймище.

## 5. Технический состав

```
Строк кода          ~12 000 (TypeScript/TSX, без node_modules)
Коммитов            93
Период разработки   1 июля — 11 августа 2026
```

**Стек:** React Native 0.81 + Expo SDK 54, TypeScript strict, Expo Router,
Zustand, TanStack Query, Reanimated 3, react-native-maps, react-native-svg,
i18next, Supabase (Postgres + Auth + Edge Functions), Yandex Cloud.

**Структура:**

```
apps/client      клиентское приложение (21 экран)
apps/executor    приложение исполнителя (6 экранов, на фикстурах)
packages/ui      дизайн-система: 21 компонент, токены, тема
packages/api     API-клиент: 13 групп, три режима (mocks/supabase/rest)
packages/store   состояние (Zustand)
packages/utils   форматирование, валидация, даты
tools/cemetery   обработка съёмки: DWG → координаты → SQL, план, PDF
supabase         схема БД, RLS, RPC, Edge Functions, импорт съёмки
```

**Качество:** `tsc --noEmit` проходит по всем шести пакетам, 30 юнит-тестов
на утилитах проходят. Сквозных автотестов интерфейса нет — сценарии
прогоняются вручную через браузерную сборку.

## 6. Ближайшие шаги по убыванию ценности

1. **Ведомость от геодезиста** (номер → ФИО → даты). Без неё 382 места
   безымянные. Это разблокирует поиск по фамилии — главный сценарий продукта.
2. **Второе и третье кладбище.** Один оцифрованный объект — это демонстрация,
   три — это уже метод, который можно масштабировать и показывать инвестору.
3. **Юрлицо и ЮКасса.** Пока нет — нет ни одного платящего клиента,
   а значит и никакой unit-экономики.
4. **Supabase Storage** для фотоотчётов. Мандаторное фото — обещание продукта,
   сейчас его технически невозможно выполнить.
5. **Приложение исполнителя на боевую базу.** Без него заказ некому выполнить.
6. **Push-уведомления** (FCM/APNs) — нужны для возврата пользователя.

## 7. Как показать продукт вживую

**Телефон:** Expo Go → QR-код ветки `preview`. Тестировщику нужен аккаунт
Expo и приглашение в организацию (роль Viewer).

**Скриншоты:** `docs/screenshots/` — 15 экранов, сняты 11.08.2026 с боевой
базы, не макеты. В подвале профиля виден режим сборки `supabase` — это
подтверждение, что данные настоящие. Для съёмки экрана «Сохранённые» в
избранное были добавлены три демо-персоны; заказы намеренно не создавались,
чтобы не искажать отчётность.

Карта на карточке памяти — статичная плитка Яндекс.Карт с меткой участка,
тап открывает Яндекс.Карты. Ключ клиентский, лежит в `MapPreview.tsx`.

**Данные кладбища для проверки:** `docs/cemetery/cemetery-plan.pdf` —
план на 5 листах A3, который можно показать заказчику или администрации
кладбища.
